## Project

Spring Boot 4.1.1 / Java 17 proof-of-concept exposing Users and Orders over GraphQL (Spring for GraphQL), backed by MySQL via Spring Data JPA and QueryDSL. Single Maven module, no README; `HELP.md` is the Spring Initializr stub.

## Commands

Use the Maven wrapper (`mvnw.cmd` on Windows, `./mvnw` in Git Bash). There is no lint/format plugin configured.

```
./mvnw clean compile                 # also regenerates QueryDSL Q-classes (see below)
./mvnw spring-boot:run               # runs on http://localhost:9091
./mvnw test                          # all tests
./mvnw -Dtest=ApplicationTests test  # single test class
./mvnw -Dtest=ApplicationTests#contextLoads test   # single test method
./mvnw package -DskipTests
```

Runtime prerequisites (also for tests, which are `@SpringBootTest` with no embedded DB):
- MySQL on `localhost:3306`, user/password `root`/`root`. The `poc-graphql` database is created automatically and the schema is managed by `spring.jpa.hibernate.ddl-auto=update`.
- Endpoints: GraphQL at `POST /graphql`, GraphiQL UI at `/graphiql`, REST image upload at `/api/users/{id}/profile-image`.
- `postman/poc-graphql.postman_collection.json` has ready-made requests for every query/mutation plus error examples.

## QueryDSL code generation

Q-classes (e.g. `com.poc.graphql.entity.QUser`) are **not** checked in. They are generated by `querydsl-apt` (jakarta classifier, configured under `maven-compiler-plugin` `annotationProcessorPaths` in `pom.xml`) into `target/generated-sources/annotations` during `compile`. If the IDE or a build reports `QUser` missing, run `./mvnw clean compile`. Adding or renaming an entity field requires a recompile before the Q-class reflects it.

## Architecture

Standard layering: `controller` → `service` (interface + `service/impl`) → `repository` → `entity`. The non-obvious parts:

**Response envelope.** Every GraphQL query/mutation returns `ApiResponse<T>` (`success`, `message`, `data`). The schema models this with per-type wrappers (`UserResponse`, `UserListResponse`, `OrderResponse`, `DeleteResponse`, ...), so adding a new operation means adding both a wrapper type in `schema.graphqls` and a controller method returning `ApiResponse<...>`. The same envelope is used for REST responses.

**Lazy relations are resolved by `@SchemaMapping`, not entity getters.** `Order.user` is `FetchType.LAZY` and `User.orders` is a lazy collection; services are `@Transactional`, controllers are not. `UserController.orders(User)` and `OrderController.user(Order)` re-query through the service layer instead of touching the proxy. Follow this pattern for any new relation exposed in the schema, and only read `order.getUser().getId()` from a lazy proxy outside a transaction.

**Two exception handlers.** `GlobalGraphQlExceptionHandler` (`@GraphQlExceptionHandler`) maps domain exceptions to GraphQL `ErrorType`s; `RestExceptionHandler` (`@RestControllerAdvice`) maps the same exceptions to HTTP statuses for the multipart endpoints. A new domain exception usually needs a case in both. Unknown exceptions are logged and surfaced as a generic "Something went wrong".

**Validation.** Input DTOs (`dto/UserInput`, `dto/OrderInput`) carry Jakarta Bean Validation annotations and are validated via `@Argument @Valid` on controller methods; violations surface as `BAD_REQUEST` GraphQL errors with the messages joined.

**Data access split.** `UserServiceImpl` builds a `JPAQueryFactory` from the injected `EntityManager` and uses QueryDSL for reads and the `userSearch` filter/pagination query, while `UserRepository`/`OrderRepository` are plain Spring Data interfaces used for writes and simple finders. Prefer QueryDSL for any new dynamic/filtered query.

**Profile images** are uploaded via REST multipart (max 2MB, JPEG/PNG/WEBP only), stored on `User.profileImage` as a Base64 data URI in a `LONGTEXT` column, and exposed read-only through GraphQL as `User.profileImage`. The `uploads/` directory is a leftover from an earlier file-system approach and is gitignored.
